# Matriz de Cobertura — Crítica Adversarial (Fase 2)

## Iteração 1 — V(1)

| id | module | lens | severity | description |
|---|---|---|---|---|
| AS-01 | networking | Assumptions | 🟡 | execute<T> não distingue HTTP 200-com-erro-embutido (padrão Moodle: login/token.php retorna 200 mesmo em falha, com {error, errorcode} no corpo) de sucesso real — assume implicitamente que status HTTP reflete sucesso de domínio |
| AS-02 | push-transport | Assumptions | 🔴 | Nenhum caminho de falha declarado para inicialização do Firebase SDK (ex.: GoogleService-Info.plist ausente/mal configurado) — o Android tinha try/catch+log explícito para um cenário análogo (falha de carregamento do certificado mTLS em NetworkModule.kt), aqui não há equivalente declarado |
| AS-03 | course-reminders | Assumptions | 🟡 | Assume que o limite de 64 notificações locais pendentes do iOS (UNUserNotificationCenter) nunca será atingido pela combinação de cursos inscritos × lembretes — não declarado como restrição nem endereçado |
| AS-04 | cert-ext | Assumptions | 🟡 | Assume que a busca por CPF (obterPessoa) sempre retorna uma pessoa única/inequívoca — nenhum tratamento declarado para resposta ambígua ou múltiplos registros |
| AR-01 | home-ui | Architectural | 🟡 | Fan-in de 7 módulos de domínio (courses, certificates, certidao, cert-ext, moodle-web, news, admin-feed) — testar home-ui em isolamento exige mockar 7 interfaces; considerar um módulo agregador/fachada |
| AR-02 | push-transport | Architectural | 🟡 | Acopla-se a admin-feed para entregar conteúdo administrativo recebido via push, mas admin-feed (M-10) não expõe, na tabela de arquitetura, um método distinto de "recepção externa" separado de fetchFeed() — acoplamento direcional implícito, não modelado explicitamente na interface |
| AR-03 | persistence | Architectural | 🔴 | SecureStore e LocalStore são dois protocolos dentro do MESMO módulo Swift, sem barreira de compilação entre eles — nada no design impede uso acidental de LocalStore para um dado sensível (ex.: token), exatamente o risco de vazamento sensível↔não-sensível que a correção de granularidade do VA-human (P0005) pretendia eliminar ao pedir "separação explícita" |
| IM-01 | cert-ext | Implementability | 🟡 | Assinatura de registrar(...) está abreviada em architecture.md ("..."); a evidência Android (CertExtRepository.kt) mostra 7+ parâmetros nomeados + upload multipart de arquivo — especificação insuficiente para implementação direta em uma única sessão sem retornar à fonte Android |
| IM-02 | courses | Implementability | 🟡 | FormularioResult e EnrollmentResult são citados como tipos de retorno mas não definidos em architecture.md — implementador precisa consultar specs/models/modelos-de-dados.md separadamente; a interface do módulo não cita essa dependência de spec explicitamente |
| SC-01 | course-reminders | Scientific | 🟢 | Domínio confirmado como não-científico na Fase 0 (technical_scientific_research = N/A); único ponto residual desta lente: os formatos de data PT-BR aceitos pelo parser heurístico são derivados empiricamente do Android, sem um contrato de origem (quais formatos o backend realmente pode emitir) documentado como fonte |
| SE-01 | persistence | Security | 🔴 | Nível de acessibilidade do Keychain (kSecAttrAccessible) não especificado no contrato de SecureStore — sem uma política explícita (ex.: afterFirstUnlockThisDeviceOnly), há risco de exposição de credencial em cenários de extração de backup/dispositivo antes do primeiro desbloqueio |
| SE-02 | networking | Security | 🔴 | A AuthStrategy .mTLSClient cobre apenas a autenticação do CLIENTE perante o servidor — a interface não declara validação/pinning do certificado do SERVIDOR além do padrão do sistema operacional; um MITM com CA comprometida na cadeia de confiança do dispositivo ainda seria viável sem pinning explícito |
| SE-03 | cert-ext | Security | 🟡 | O fluxo de upload de PDF (registrar) não declara validação de tamanho/tipo de arquivo no lado cliente antes do envio — dependência total de validação do backend, sem guarda-corpo local |
| SE-04 | push-transport | Security | 🟡 | O campo actionUrl do payload de push, se herdado literalmente do comportamento Android (abre qualquer URL via ACTION_VIEW-equivalente), permite que o remetente do push (backend/painel) faça o app abrir qualquer URL, sem allowlist de domínio — vetor de phishing/open-redirect caso o canal FCM ou a conta do painel seja comprometido |
| PE-01 | courses | Performance | 🟡 | Endpoints com automação Puppeteer no backend ([latência típica observada], evidenciado em specs/technical/integracao-apis.md) não têm política de timeout diferenciada declarada em execute<T> genérico — mesmo achado aplica-se ao módulo news (duplica: PE-01) |
| PE-02 | admin-feed | Performance | 🟢 | Persistência serializa a lista completa a cada escrita (padrão herdado do Android, JSON em chave única) — aceitável na escala atual (dezenas de itens), mas não escalável sem revisão futura |
| RE-01 | persistence | Regulatory | 🟡 | CPF (dado pessoal sob a LGPD) é armazenado localmente sem classificação de sensibilidade declarada entre SecureStore e LocalStore — arquitetura não determina em qual dos dois ele deve residir |
| RE-02 | cert-ext | Regulatory | 🟡 | Nenhum módulo documenta a base legal/finalidade (LGPD) para o tratamento de dados de certificação profissional — provavelmente coberta pelo contexto institucional (TJAC/ESJUD), mas não rastreável a partir da arquitetura |
| RS-01 | courses | Resilience | 🔴 | Endpoints com automação Puppeteer no backend podem travar/falhar sem resposta rápida; nenhum contrato de timeout+cancelamento do lado cliente foi declarado (duplica em news) |
| RS-02 | push-transport | Resilience | 🟡 | O backend (painel-web) já degrada com graça para o app poder usar polling de feed quando o push falha (A-3/A-4), mas o cliente iOS não declara um contrato equivalente do lado dele (ex.: "se nenhum push chegar em N minutos, disparar poll de admin-feed") |
| RS-03 | networking | Resilience | 🔴 | Nenhum comportamento declarado para falha de carregamento do certificado cliente mTLS (arquivo ausente, senha incorreta) — risco real de repetir a degradação silenciosa observada no Android (NetworkModule.kt cai para cliente sem mTLS, gerando 400/401/403 confusos sem sinalização clara ao usuário/desenvolvedor) |
| UX-01 | courses-ui | UI/UX | 🟡 | Sem estado de loading/cancelamento explícito desenhado para chamadas de [latência típica observada] — risco de o usuário perceber o app como travado (relacionado a RS-01) |
| UX-02 | cert-ext-ui | UI/UX | 🟡 | Fluxo multi-etapa (tipo → obter pessoa → formulário → upload) sem contrato de recuperação de estado se o app for suspenso pelo sistema durante a seleção de arquivo PDF (troca para o app Arquivos) — classe de bug real e comum em apps iOS |
| UX-03 | notifications-ui | UI/UX | 🟢 | Sem estado vazio/first-run declarado para quando não há notificações |
| ET-01 | cert-ext | Ethical / Human Impact | 🟡 | Uma falha silenciosa no registro de certificado pode levar a pessoa (servidor/magistrado) a crer que um registro profissional foi concluído com sucesso sem que de fato tenha sido — nenhum contrato de confirmação/recibo explícito foi declarado |
| ET-02 | auth | Ethical / Human Impact | 🟢 | Nenhum requisito de acessibilidade (ex.: VoiceOver) declarado para o fluxo de login, apesar da base de usuários incluir servidores/magistrados de perfis variados |
| PW-01 | cert-ext | Process / Workflow | 🟡 | A máquina de estados de idSituacao (evidenciada no Android: 1 = "em análise", demais valores não documentados) não tem, na arquitetura, um módulo/responsabilidade explícita para mapear todos os valores possíveis e seu significado ao usuário — risco de estado não tratado na UI |
| PW-02 | courses | Process / Workflow | 🟡 | O mapeamento de códigos HTTP 409/422/500 para FormularioResult/EnrollmentResult é implícito (herdado da evidência Android), não explicitado como parte do contrato do módulo em architecture.md |
| PW-03 | admin-feed | Process / Workflow | 🟢 | Nenhum processo de reconciliação declarado para quando o mesmo item de notificação chega primeiro via push e depois via poll de feed — deduplicação por id é um padrão evidenciado no Android (AdminNotificationsStore.prepend), mas não atribuída explicitamente a um módulo na arquitetura iOS |
| OB-01 | networking | Observability / Operability | 🔴 | Nenhum módulo possui responsabilidade declarada de diagnóstico/log centralizado — sem isso, falhas como RS-03 (degradação silenciosa de mTLS) ou SE-02 (ausência de pinning) seriam praticamente indetectáveis em produção sem relato manual do usuário |
| OB-02 | push-transport | Observability / Operability | 🟡 | Nenhuma métrica declarada de taxa de sucesso/falha de entrega de push — impossível validar em produção, ao longo do tempo, se as premissas A-3/A-4 (compatibilidade do backend com iOS) continuam se sustentando |
| LG-01 | certidao | Linguistics / Grammar | 🔴 | O campo period da API de Certidão é polimórfico — número JSON (modo retroativo) OU string JSON (modo ano/mês), conforme PeriodoConfig.toApiValue() evidenciado em specs/models/modelos-de-dados.md — contrato ambíguo o suficiente para que duas implementações Swift corretas (ex.: um model Codable com tipo fixo) divirjam e quebrem silenciosamente |
| LG-02 | cert-ext | Linguistics / Grammar | 🟡 | O campo curso_credenciado ("S"/"N") — booleano codificado como string, ou um enum com mais valores possíveis no futuro? Ambiguidade já registrada em specs/references/perguntas-para-va-human.md, herdada sem resolução pela arquitetura |
| LG-03 | cert-ext | Linguistics / Grammar | 🟡 | Divergência já evidenciada entre um comentário de código (http://...:8080/) e a constante realmente usada (HTTPS, sem porta) para a URL de produção da API de Certificados Externos — a arquitetura não resolve qual delas é autoritativa antes da implementação |
| MEC-01 | networking | Mechanical Engineering | 🟡 | iOS 17+ (D0010) cobre múltiplas versões menores do sistema e hardware variado (de dispositivos mais antigos suportados a mais recentes) — nenhuma política de tolerância declarada para eventuais diferenças de comportamento TLS/mTLS entre versões menores do iOS |
| MEC-02 | push-transport | Mechanical Engineering | 🟡 | O SDK do Firebase para iOS é uma dependência de terceiros com ciclo de release independente da Apple — nenhuma política de compatibilidade/tolerância de versão declarada (mínima/máxima suportada) |
| MEC-03 | courses | Mechanical Engineering | 🟢 | Nenhuma tolerância declarada para variação de qualidade de rede (3G/Wi-Fi fraco) além da latência fixa já conhecida do backend ([latência típica observada]) |
